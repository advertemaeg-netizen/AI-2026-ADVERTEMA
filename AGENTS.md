# Database migrations: do not use a real timestamp

The filenames in `supabase/migrations/` run ahead of the calendar, so a file made by `supabase migration new` (or named with today's date) sorts before migrations that are already applied. Read `supabase/README.md` before adding one: name it after the highest timestamp in `supabase/migrations/` and `supabase/pending/`, and never pass `--include-all` to `supabase db push`.

# Before committing: `npm run check`

Run `npm run check` after the last edit and before every commit: `tsc --noEmit` over the whole repo (test files included), then `eslint`, then `vitest run`. Vitest alone does not type-check: commit eb21545 landed a test that broke `tsc` while every test passed. The multi-message webhook tests have a known flake: `messages` and `leads` are ordered by `created_at` alone, and rows come back in the wrong order (seen 2026-10-19: the bot answered a visitor's first message in reply to their second). The first dumps show no timestamp ties; the first visitor message was stamped over a second later than rows written after it, which may be the test database's (PGlite's) clock rather than production's. That is open. Report such a failure with what it read; don't rerun until green and call it clean.

**The ordering defect's count: 4 appearances** (2026-11-12: run 20 ×3 — booking-order, branch-day-check, whatsapp-reply voice note; run 24 ×1 — whatsapp-reply image and document). Update this line every time it appears, with the run and the test. A rerun past it is the owner's call, one at a time, and named in the commit; the count is what makes the case for fixing it.

**Time ordering in this test harness is unreliable by default.** The tests' database (PGlite) has stamped a row over a second in the future and a lead after its own `updated_at`, and it keeps milliseconds where production Postgres keeps microseconds. A test that needs an order should assert on something deterministic (the sequence it wrote, a reply's content, a counter), not on `created_at` or `updated_at`; and a test of code that orders by time stands on that clock, so read its failures with that in mind.

The evidence is kept for you: `npm run check` (`scripts/check.sh`) writes everything it prints to `.scratch/check-failures/check-<time>-<commit>.log`, deletes it when the run is clean, and keeps it when the run fails, with the commit and the working tree's state at the top. Each kept failure of a webhook test is a data point on the ordering defect's mechanism — for example, whether the rows read in the wrong order share a `created_at` — so don't delete them; collect them for the ordering fix.

## Interim rule: the access project's stuck state (adopted 2026-11-09; ends when option 2 lands)

**This predates the Facebook build, and predates 2026-11-09.** Some runs of the access project (`tests/access`) switch into a state where every request takes about 10 s, and never recover: tests time out one after another and the files after them fail on `PGRST000` / "Database connection error". It was first recorded on 2026-10-25 (commit 26cf013: "about one run in three that connection wedges"), and on 2026-11-09 counted again at 3 runs in 10 of the access project alone (a count since found unreliable: see below). Until then it was read as a connection flake each time, and at least one commit was cleared by rerunning (3823805, 2026-11-01: "clean on the third run"). So for two weeks, some green access runs may have been green only because the failing ones were rerun: don't assume this arrived with any one change. The full diagnosis, including what is still not known (what triggers it, and, unproven, whether pglite-socket's single connection slot stays taken: see the proposed mechanism below), is in `tests/harness/access-fetch.ts`, "THE STUCK STATE". Splitting tests and raising their limits do not help with it: in the stuck state test size is not what fails.

**There is a second way the access project fails, and it is not the stuck state.** A test can outgrow its limit: it times out with **no `[access] slow reconnect` marks and no cascade** (the tests after it pass), because it simply takes longer than its limit allows. That is a **real failure**, never rerun. It is what failed on 2026-11-09: the channel-secrets matrix, six tables in one test, 86–96 s alone and over its 120 s in a full run sharing the machine. The cure for this one *is* splitting (that test is now one test per table, ~14 s each alone, 20–25 s in a full run); if a split test ever outgrows its limit, stop and report, and do not raise the limit. The distinction: **marks plus a cascade is the stuck state; a timeout without them is a test outgrowing its limit.**

**A run can end four ways, and the rule covers only two of them** (recorded 2026-11-09, run 7). It can end clean; stuck (above); in a real failure (above); or **never end at all**. In run 7 the tests finished, vitest printed its summary at 15:52, and the process never exited: the access project's PostgREST went on retrying its connection for 55 minutes until the run was killed. A hang is its own shape. It is not the stuck state and not a pass, and the rule gives it no rerun: kill it, keep its log, report it. Whoever starts a run watches for it: a run past half again its expected time is checked on, not waited for.

**The app project can have an outage too, and nothing classifies it.** Also in run 7, the app project's own PostgREST backed off to 16 s (no `T` byte, never stuck) and 80 app tests failed, every one on a connection error, not one on an assertion about the code. Nothing we built was broken. But this rule was written for the access project alone: an app-project failure is `NOT STUCK` by the script and blocks the commit, with no way to tell an outage from a bug. That is a gap, recorded here rather than papered over; it closes with the cure, not with a wider rule. Since 2026-11-10 the app project retries a connection-type 503 (PGRST000–003, nothing else, bounded) exactly as the access instrument always has (`withConnectionRetry`, `tests/harness/helpers.ts`): run 8's one failure was a single dropped connection the app project did not retry. **Every retry logs `[harness] connection retry`. Count them in a failed run's log: if the number climbs from run to run, the harness is rotting, and the retry is hiding it.**

**A proposed mechanism, parked (2026-11-09: worth hours later, zero minutes until the Meta submission is in).** The first in two weeks. In the one stuck run with PostgREST's log on, at the moment it went stuck PostgREST's connect attempt received `T` where the protocol's first reply belongs: the first byte of `Too many connections`, which pglite-socket writes when it refuses a connection because its single slot (`maxConnections` defaults to 1) is counted as taken. From then on every reconnect failed, and PostgREST's backoff doubled 1, 2, 4, 8, 16 s and sat at its 32 s cap for the rest of the run; in a run that did not go stuck, about 1,900 dropped connections all reconnected within 1–4 s. Hypothesis: a connection that drops under a refused statement (pglite#958) is never removed from pglite-socket's count, so its one slot stays taken and every new connection is refused for good. **What would test it:** an access-project run on its own with `HARNESS_LOG_DIR` and `HARNESS_SOCKET_LOG=1` that goes stuck should show `handleConnection: max connections reached, rejecting` again and again in the socket log; if it does, giving the socket more than one slot (or fixing or upgrading its cleanup) should take the stuck rate to zero over ten runs. That would be a cure costing hours, against option 2's day and a half. Unproven: one `T`, in one run.

**The "3 in 10" is not reliable.** It was counted by eye, before the signature script existed, on runs whose split channel-secrets test turned the stuck state into a snapshot mismatch (run 7) and whose logs were cut off before their failures printed (runs 3 and 10); all ten also carried a real assertion failure of their own. Not reopened (2026-11-09); remeasure through the script when the stuck state is next worked on.

**What the measurement bought was the signature script, not the split.** Before `scripts/access-stuck-signature.mjs` there was no way to tell a flake from a bug: every access failure looked like "connection errors". That is why this diagnosis moved four times in one night (a connection flake; a cost growing with each table; a stuck state with test size irrelevant; then two modes), and why the Instagram DM build (21d48e4) shipped on a misreading and was right only by luck. Read a failed access run through the script before forming any view of it.

Until the stuck state is cured, a failed `npm run check` may be rerun **only** under all of this:

1. **The script decides, not the eye.** `node scripts/access-stuck-signature.mjs <the run's log>` must print `STUCK`. It says so only when the log is whole, no app-project test failed, every access failure is a timeout or a connection code (one real assertion, a snapshot mismatch or any other error anywhere and it is not), at least one test timed out, at least three `[access] slow reconnect` marks are present (the state's positive sign, written by the access instrument), and no single request hung (no wait over 15 s, no 90 s watchdog). `NOT STUCK` blocks the commit like any failure. The script's own tests (`tests/checks/access-stuck-signature.test.ts`) hold it against twelve real logs, all of which it must refuse.
2. **At most two reruns per commit.** Three stuck runs in a row stop the commit; the owner decides.
3. **A stuck run proves nothing either way.** It is no evidence against the change and none for it. A change that touches what the access tests cover (`supabase/migrations`, grants, policies, `tests/access`, the harness) needs the access project to pass outright in a run; a stuck run does not stand in for that.
4. **Every run is reported.** Every run's log is kept, none deleted, and the commit message names each run, its verdict and its log, the stuck ones included.
5. **The rate is watched.** If more than half of the last ten recorded runs are stuck, the rule is suspended: something changed, and that is a finding, not a reason to rerun.
6. **Nothing else.** It applies to no other failure: not the webhook ordering defect above, not a timeout without the script's `STUCK`.

Collect the evidence while it lasts: run the check with `HARNESS_LOG_DIR=<dir>` and the harness writes each project's PostgREST log (its connection pool's events among it), timestamped, to that directory (`tests/harness/stack.ts`); cheap enough for a full check. pglite-socket's log is `HARNESS_SOCKET_LOG=1` on top, and only for the access project run on its own (`npx vitest run --project access`): in a full check both projects' socket lines land in one file, and its volume (240 MB, 2026-11-09) slows the run enough to change the measurement. A stuck run with both logs answers which side stops reconnecting. The cure, option 2, is asserting refusals inside the database (as `test_sqlstate` does), where the connection never sees one; it is scheduled for after the Meta App Review submission, at about a day and a half. When it lands, delete this section.

# Running the production build locally: bind 0.0.0.0, as the container does

To test the marketing site's hosts against `node .next/standalone/server.js`, start it with `HOSTNAME=0.0.0.0` (the Dockerfile's value), not `127.0.0.1`. With 127.0.0.1, every site page 404s from the first request, a failure production cannot have. The proxy rewrites to `new URL(to, request.url)`, and the middleware sees `request.url` as `localhost` while Next's own origin for the request is `127.0.0.1`. The origins differ, so Next treats the rewrite as external and sends it back to itself without the site's Host, where the proxy answers 404. Found 2026-10-20; it cost an hour to tell apart from the real site outage.

Copy `public/` the way the Dockerfile's `COPY` does, by merging its contents (`cp -a public/. <dir>/public/`). The standalone output already has a `public/`, so `cp -a public <dir>/public` nests the copy as `public/public` and the brand files 404.
