# خطة إصلاح نموذج الليدز

> **المبدأ:** الليد **حلقة بيع (episode)**، مش محادثة.
> المحادثة ممكن تحمل حلقات كتير على مدى الوقت، وواحدة **مفتوحة** بس في كل لحظة.

**التوقيت:** تتنفّذ دلوقتي لأن مفيش بيانات حقيقية. كل ليد موجود بيبقى "الحلقة الأولى" تلقائياً — مفيش backfill ولا دمج.

---

## حقائق من التشخيص (متعيدش اكتشافها)

- `UNIQUE (conversation_id)` اسمه `leads_conversation_unique` في `20260930100000_leads_system.sql`
- المواعيد **أعمدة على `leads`**: `appointment_at`, `appointment_confirmed`, `appointment_reminder_sent_at`, `showed_up`, `arrival_confirmed_at`, `no_show_reason`
- `enum lead_status` في `initial_schema.sql:125`: `new`, `contacted`, `appointment_booked`, `showed_up`, `no_show`, `lost`
- `lead_events` مربوط بـ `lead_id` (مش `conversation_id`)، وبيتكتب بـ trigger `record_lead_events`
- التحليل: `detectLead()` في `src/lib/ai/lead-detection.ts`، بينده من `app/api/webhook/website/[channelId]/route.ts:277` جوه `after()`
- البحث عن الليد: `.eq('conversation_id', ...).maybeSingle()` (سطور 193–198)
- الخروج المبكر لما الـ patch فاضي: سطر 250
- مسار الفريق: `src/lib/actions/appointments.ts`
- trigger `sync_lead_attendance` بيعدّل الحالة لوحده
- مفيش جدول `customers`/`contacts`. مفيش webhook لواتساب ولا ماسنجر في الكود أصلاً
- معالجة خطأ 23505 بتمنع التكرار فعلياً — **اتأكدت 10/10** ولازم تفضل

## الطبقة 1 — توقيف النزيف (مستقلة، تنزل لوحدها)

- [ ] **أ.** `scheduleLeadDetection` يشتغل حتى لو الرد فشل (503/timeout). دلوقتي الرسالة ما بتتحللش خالص والليد بيضيع في صمت
- [ ] **ب.** `sync_lead_attendance` يبطّل يصفّر `showed_up` و`arrival_confirmed_at` لما الفريق يحجز زيارة جديدة (محتاج migration)

## الطبقة 2 — نموذج الحلقة

- [ ] **ج.** استبدال الـ constraint بـ partial unique index:
      `CREATE UNIQUE INDEX one_open_lead_per_conversation ON leads (conversation_id) WHERE status NOT IN ('showed_up','no_show','lost');`
- [ ] **د.** `detectLead` يدوّر على الليد **المفتوح**؛ لو مفيش وفيه نية ≥ 0.7 → ينشئ حلقة جديدة
- [ ] **هـ.** إلغاء الخروج المبكر — `ai_extracted_data` تتخزن دايماً حتى لو الـ patch فاضي
- [ ] **و.** الفريق يحجز على ليد نهائي → ليد جديد، مش تصفير القديم
- [ ] **ز.** الواجهة: تاريخ حلقات المحادثة، وسم "عميل راجع"، الزيارات السابقة ظاهرة
- [ ] **د-2.** التحليل للعميل الراجع يشوف الرسائل من بعد آخر حالة نهائية بس (اتنقلت من "لاحقاً": من غيرها "شكراً" بعد الحضور بتفتح ليد #2 من الطلب القديم)

## الطبقة 3 — الحجز الصادق

- [ ] **ح.** مُحلِّل موعد **واحد**. التحليل بيخزّن، والرد بيقتبس المخزّن. مفيش تفسيرين مستقلين
      (سبب إن "6 المغرب" اتخزنت 19:00 مرة و18:00 مرة والبوت بيقول 6)
- [ ] **ط.** إعداد `auto_confirm_appointments` لكل عميل في `bot_settings` — **افتراضياً شغّال**

## لاحقاً (مش الأربعاء)

- معدل الحضور بتاريخ **الموعد** مش تاريخ إنشاء الليد (غلطة قائمة دلوقتي، مستقلة)
- مقاييس التكرار: ليدز جديدة مقابل راجعة، نسبة العملاء المتكررين
- الرقم المُطبَّع يتخزن على كل ليد (مفتاح جاهز لـ `Customer` لو احتجناه)
- الكتابة مشروطة بـ `updated_at` بدل عمياء
- ليد `lost` ما ياخدش موعد وهو فاضل `lost`
- مدة انتهاء لمحادثة الويدجت

## مش هنعمله

**كيان `Customer` مستقل.** مفيش webhook لواتساب ولا ماسنجر أصلاً، فمشكلة "نفس الشخص على قنوات مختلفة" نظرية بالكامل. ولما Meta تدخل، الرقم نفسه بيبقى معرّف الـ thread.

## القرارات (متسألش عنها تاني)

| القرار | الإجابة |
|---|---|
| الحالات النهائية | `showed_up`, `no_show`, `lost`. أما `appointment_booked` وعدّى وقته — **مش نهائي**، يظهر للفريق كـ "محتاج تعليم" |
| العميل الراجع | ليد جديد، يدخل الفانل والتبويب الجديد |
| معدل الحضور | لكل زيارة |
| وحدة العد | المحادثة (دلوقتي) |
| الذكاء الاصطناعي يبطّل يحرّك الموعد | أول ما الفريق يلمسه أو وقته يعدّي |
| الفريق يحجز لليد اللي حضر | ليد جديد، والقديم يفضل بحضوره |
| سلوك البوت | ما يدّعيش تسجيل إلا لو اتسجل فعلاً |
| تاريخ التحليل | من بعد آخر حالة نهائية |
| فشل الرد | غير مقبول إنه يمنع التحليل |
| ساعة + جزء من اليوم | مُحلِّل واحد، والرد يقتبس المخزّن |
| ليد `lost` رجع يحجز | ليد جديد |

## الاختبارات (تتحفظ في المستودع)

سيناريوهات التشخيص تتحوّل regression tests — ودي كمان بتقفل فجوة "مفيش اختبارات محفوظة" المذكورة في الـ BRD:

1. عميل جديد → نية → ليد #1
2. نفس المحادثة، رسالة زيادة → تحديث ليد #1
3. ليد #1 = حضر → العميل يرجع بنية جديدة → **ليد #2**
4. ليد #1 = حضر → العميل يقول "شكراً" → **مفيش ليد #2**
5. عميل راجع بنية جديدة بلا اسم أو رقم → ليد #2
6. موعد ليد #1 **يفضل موجود** بعد إنشاء ليد #2
7. **ليد مفتوح واحد بس** في أي لحظة (اختبار الـ index)
8. 3 رسايل متزامنة → ليد واحد بالظبط
9. الرد فشل → التحليل يشتغل برضه
10. الفريق يحجز لليد اللي حضر → حضوره ما يتمسحش

اللوجات الأصلية في `docs/diagnosis/`.
